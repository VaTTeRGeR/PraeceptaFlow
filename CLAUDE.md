# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

PraeceptaFlow: a prototype desktop editor for flow graphs that represent program structure, built on PySide6's Graphics View framework. Windows is the development platform; the helper scripts are `.bat` files, with untested `.sh` counterparts for Linux and macOS.

## Commands

All commands use the project venv at `.venv` (Python 3.14, which requires PySide6 6.10 or later).

| Task | Command |
|---|---|
| Run the app | `run.bat [file.pfg]` (no console window, uses `pythonw.exe`) |
| Run the app with a console | `run_console.bat [file.pfg]` or `.venv\Scripts\python.exe src\main.py [file.pfg]` |
| Run the format tests | `.venv\Scripts\python.exe tests\test_formats.py` |
| Run the editor tests | `.venv\Scripts\python.exe tests\test_editor.py` (offscreen) |
| Install dependencies | `.venv\Scripts\python.exe -m pip install -r requirements.txt` |
| Set up the venv for building | `setup.bat` (creates the venv if missing, installs `requirements-build.txt`) |
| Build a PyInstaller bundle | `build.bat [--onefile]` (packaging only, needs the venv from `setup.bat`) |
| Remove `build\` and `dist\` | `clean.bat` |

The tests are plain asserts (no test framework). `tests\test_formats.py` covers the two text formats shared with `INSTRUCTIONS`, the `*.pd` export and the tag comments; extend it when either format changes. `tests\test_editor.py` covers the connection rules, decisions, groups and logical groups on a scene without a window, and the `.issues` file on a `MainWindow`. No linter is configured.

`setup.sh`, `build.sh` and `run.sh` are the Linux and macOS counterparts (venv paths under `.venv/bin`; `run.sh` covers both run scripts; on macOS `build.sh` produces `dist/PraeceptaFlow.app` and rejects `--onefile`). They need LF line endings (`.gitattributes`) and the executable bit, which Windows cannot set: `git add --chmod=+x`.

`build.bat` builds a windowed executable named `PraeceptaFlow`. `*.spec` files are git-ignored and regenerated by PyInstaller.

### Checking GUI changes without a display

Set `QT_QPA_PLATFORM=offscreen`, construct `MainWindow`, and drive it with `PySide6.QtTest.QTest`. Two things to know:

- The offscreen platform has no fonts, so text renders as boxes and text widths are wrong. Use the native platform for screenshots (`widget.grab().save(...)`).
- `QTest.mouseDClick` sends a bare double-click event. Qt's scene turns that into a plain press unless the same item received the preceding press, so simulate a real double-click as `mouseClick`, then `mouseDClick`, then `mouseRelease`.

## Architecture

`src/main.py` is the entry point and is run as a script, so `src/` is the import root: modules import each other as `from editor.x import ...`, not `from src.editor...` and not relatively. PyInstaller relies on the same layout.

The editor lives in `src/editor/`:

- **`items.py`**: the graphics items. `NodeItem` is a box centred on its position with a title and a wide border (`BORDER_WIDTH`) that edges are dragged from. `EdgeItem` is a curved arrow between an anchor on each node's outline, leaving each node at a right angle. `EdgeHandle` is the draggable circle at each end (the node's body is cut out of the painted circle, so it looks half-hidden). `EditableText` is the in-place text editing, used for the node title. The title is multi-line and centred: Enter inserts a line break, Ctrl+Enter or Escape ends the edit. Qt only centres lines within a fixed text width, so `NodeItem._layout` sets the title's text width to its widest line (measured unbounded first, or the old width would wrap typing) and runs on `contentsChanged`, because with a fixed width `documentSizeChanged` no longer fires when the text shrinks.
- **`scene.py`**: `EditorScene` owns the mouse interaction (dragging from a node's border to create an edge, recording moves), the grid background, and `to_dict` / `load_dict`.
- **`view.py`**: `EditorView` handles zoom and pan only.
- **`commands.py`**: the `QUndoCommand` subclasses.
- **`export.py`**: `project_description`, which turns the dict from `EditorScene.to_dict` into the text of a project description (`*.pd`). It works on the dict, not on scene items.
- **`claude_runner.py`**: `ClaudeRunner`, which runs `claude -p` (stream-json) in a folder and turns its events into lines of text; `ClaudeSetup`, which checks the install and login and lists the models; also holds the two prompts.
- **`instructions.py`**: `INSTRUCTIONS`, the system prompt for those runs as a string constant, so it is part of the app (and of a PyInstaller bundle) instead of a file to locate.
- **`source_map.py`**: finds the tag comments in the generated source files (no Qt); `scan(folder)`.
- **`code_view.py`**: `CodeView`, the read-only code pane: whole files, syntax colours from Pygments, the selected node's code tinted and the rest grey.
- **`main_window.py`**: menus, file handling and modified-state tracking.

### Things that span several files

- **There is no separate graph model.** The scene items are the document. Each item has `to_dict` / `from_dict`, and `EditorScene.to_dict` / `load_dict` assemble the file (JSON, `*.pfg` for "ProjectFlowGraph", with a `version` field checked against `FORMAT_VERSION`). Introducing a view-independent model is the intended next step before validation or code generation.
- **All structural changes go through the undo stack.** Add, delete and move push a command onto the `QUndoStack` created in `MainWindow` and shared with the scene. Commands call `EditorScene.add_item` / `remove_item`, never `addItem` / `removeItem` directly, because those two methods also maintain each node's `edges` list.
- **Box types are a field, not classes.** `NodeItem.kind` is a `NodeKind` from the `NODE_KINDS` table in `items.py` (label, `color`, `outgoing`, `incoming`, `arrow_head`), stored in the file as the table key in the node's optional `type` field (`DEFAULT_KIND` when absent). The label is painted on the top border, which takes the kind's `color`; the body is a light tint of it. The selection ring is drawn outside the box so the colour stays visible when selected. `connection_error` is the one place that decides whether an edge is allowed; the scene's edge drag and `EdgeItem.from_dict` both use it. An edge drops its arrow head (`EdgeItem.has_head`) if either end's kind has `arrow_head=False`. The Insert menu is generated from the table.
- **A kind's `links` override `outgoing` / `incoming`.** `NodeKind.links` names the kinds a kind may always connect to (`"*"`: any, in either direction): a Data Output to a Data Input, a Tooling Note to everything. `NodeKind.starts_edges` (not `outgoing`) decides whether a border starts an edge.
- **Never call `parentItem()` on an item that may have no parent.** PySide then forgets that the scene owns the item, and it is deleted with its last Python reference (nodes vanish after a load). Use `NodeItem.decision` (set only on a `CaseItem`) or `isinstance(item, CaseItem)`.
- **A decision is a header with child items.** `DecisionItem` (kind `decision`, incoming only) owns `cases`, a list of `CaseItem`s (kind `case`, outgoing only, `insert=False` keeps it out of the Insert menu) that are its child graphics items; the list order is the order of evaluation. An edge out of a branch has the `CaseItem` as its `source`, so anchors and handles work unchanged; an edge dropped on a case ends on the decision (`EditorScene._target_at`). `DecisionItem._arrange` gives header and row one width and the cases one height. Cases are not selectable: a press selects the decision, a horizontal drag reorders (live through `set_cases`, then one `SetCasesCommand`). The `+` / `-` `CircleButton`s call `EditorScene.set_cases`, a macro that first deletes the edges of a dropped case. The file stores `"cases": [{"id", "title"}]` on the node, and `load_dict` adds the case ids to the map edges are resolved against. `make_node(kind)` picks the class; `to_dict`, `_nodes()` and the parity badges skip cases.
- **Groups are a field, and one scene holds every canvas.** A node or logical group on the sub-canvas of a group node (kind `group`) has that node as its `group` (file: optional `"group": <id>`); `group_of` gives it for edges and handles too. `EditorScene.current_group` is the canvas shown: `enter_group` and `add_item` set items visible only if their group is the current one, and `remove_item` leaves a canvas whose group is removed. So code that walks `scene.items()` sees all canvases: check `isVisible()` (Select All, `visible_rect` for Fit All) where only the shown one is meant. A double-click on a group outside its title enters it; the breadcrumb label over the view (`MainWindow._crumbs`) and View > Leave Group (Alt+Up) go back. `DeleteItemsCommand` takes everything inside a deleted group. Undo can change a canvas that is not shown.
- **A logical group is a `RegionItem`, not a node.** Position is its top left, `size` its extent; `shape()` is only the header strip and the border, so the canvas under it keeps working. A border drag resizes (`SetGeometryCommand`), a header drag moves it and carries its `members()` (items whose centre lies on it): `EditorScene.mousePressEvent` calls `carry(True)` and records the members' positions, so the one `MoveItemsCommand` covers them. The file stores them in a third list, `regions`.
- **Edges are tracked on both ends.** `NodeItem.edges` lists every attached `EdgeItem`; the node calls `edge.update_path()` when it moves or its size changes. `DeleteItemsCommand` uses the same list to remove and restore the edges of a deleted node.
- **Edge handles are separate scene items.** Each `EdgeItem` owns two `EdgeHandle`s that `EditorScene.add_item` / `remove_item` add and remove with it. They sit above the nodes (z=2; the edge itself is at z=-1) because their circle overlaps the node's border, and `EditorScene.mousePressEvent` lets a press on a handle through instead of starting a new edge. Dragging one slides that end along the same node's outline and pushes a `MoveAnchorCommand`.
- **Edge ends are anchors, not fixed points.** An anchor is a point on the node's outline stored as fractions of the box's half size (one coordinate is always ±1), so it keeps its relative place when the title changes the box size. `NodeItem.anchor_at` / `anchor_pos` convert to and from scene positions. The anchor lies on the bounding rectangle, but the part of a side within `CORNER_RADIUS` of a corner is bent onto the rounded corner (`_outline_point`), so the edge leaves at an angle between 0° and 45° there; `anchor_normal` gives that direction. The file stores them as optional `source_anchor` / `target_anchor` pairs; an edge without them gets anchors facing the other node at load time.
- **The canvas context menu is the Insert menu.** `EditorView.contextMenuEvent` emits `canvas_context_menu` for a right-click on empty background, and `MainWindow._show_canvas_menu` execs the same `QMenu` the menu bar uses, so new Insert actions appear in both. `MainWindow._insert` places the new item at the click (`_insert_pos`) or, for a shortcut, at the pointer if it is over the viewport (`_pointer_scene_pos`), snapped to the grid. Picks from the menu bar fall back to the view centre with a stagger, because the pointer is then over the dropdown (`_insert_menu_open` tracks that).
- **Text edits bypass the undo stack.** `EditableText` emits `EditorScene.text_edited` when an edit ends with changed text, and `MainWindow` keeps a separate `_text_dirty` flag. The window is modified when that flag is set or the undo stack is not clean.
- **The project description (`*.pd`) is derived from the graph and rewritten on every save, every open and on close.** `MainWindow.save_file` writes the `.pfg` to `<name>.pfg.tmp` and swaps it in with `os.replace`, so a failed write keeps the old graph. `MainWindow._export_beside` writes the description next to the `.pfg` (a failure is reported but the save or open still succeeds); there is no menu item. On close it is only rewritten when the window is not modified, so discarding changes leaves the `.pd` matching the file on disk. It is plain text made of lists: `Project Notes:` first, then the tooling notes that are not connected to a step, then `Logical Groups:` with one item (`[hash] Title`) per region that holds a step, then `Program Flow:` with one item per step (the kinds in `STEP_KINDS`), then the implementation notes that are not connected to a step. A step is identified by a hash, the first `MIN_HASH_LENGTH` characters of the node's id (longer for all nodes if two would collide), and names the steps its edges lead to under `Next:` (`end` if there are none). A step's whole title stays together as one list item (further lines continue it); `Next:` and the note headings are plain indented lines, not list items. Every note item (project notes too) also starts with its own hash, which is only there so a generation can report on the note; it never appears in source code. `INSTRUCTIONS` in `instructions.py` documents this format for the agent, so change both together. Implementation and tooling notes (`NOTE_HEADINGS`) are listed under every step they share an edge with, whichever end they are on. Steps are in flow order (topological, ties and cycles by position, top to bottom). A `Decision` step has `Cases:` instead of `Next:`, one list item per case with its own `Next:`. Groups are not steps: the flow is flattened through them (an edge into a group leads to the members nothing leads to, the last steps inside go on with what the group leads to, an empty group passes the flow on), and each step inside gets a `Group:` line with the group titles, outermost first. `Logical group:` names the regions whose rectangle holds the step's position by their own hashes only (`[hash], [hash]`, the region ids count for the hash length too; the titles are in `Logical Groups:`, so renaming a region does not change its steps' items): the generated code of a region is wrapped in tag comments of that hash, around its steps' sections and the code that only supports them. A note connected to a group is listed under every step inside it.
- **The Source Generation menu runs Claude Code on the `*.pd`.** `Generate Source Code` (Ctrl+G) pipes the description to `claude -p` with `INSTRUCTIONS` appended to the system prompt (`--append-system-prompt`), in the `.pd`'s folder, with `acceptEdits`. `Check Parity` (Ctrl+Shift+G) uses the same instructions but a prompt that only compares source and description; edit and shell tools are denied. Both save first without asking (`_save`, so an untitled graph gets the Save As dialog; there is no way to run on a discarded state) and send the description built from the canvas, not the `.pd` read back from disk. A generation asks before it starts if the folder holds another `*.pfg`, because it removes the code of tags it does not know. `GENERATE_ARGS` denies the shell tools like `PARITY_ARGS` does. Both log what Claude says and which tools it uses into the bottom "Claude" dock (View menu toggles it). The `claude` command must be on `PATH`. Closing the window while it runs asks, then kills the process. The same menu has `Model` and `Effort` submenus whose choices are appended as `--model` / `--effort` to both commands (`MainWindow._model_args`); "Default" passes no flag, so the user's own claude settings decide, and the choice is not persisted. The lists are not hard-coded: `ClaudeSetup` (`claude_runner.py`, started by `main.py` through `MainWindow.start_claude_check`) checks that `claude` is on `PATH`, that `claude auth status --json` says `loggedIn`, then sends the stream-json `initialize` control request (claude has no model-listing command) and uses the `models` of the reply (`value`, `displayName`, `supportsEffort`, `supportedEffortLevels`). A problem is shown as a dialog (with a Log in button that runs `claude auth login` and re-checks); until claude answers, or if it cannot, both submenus only hold "Default". The effort menu is rebuilt from the selected model's levels and disabled for models without effort support.
- **A generation reports how each note was realized.** `GENERATE_ARGS` passes `--json-schema` with `NOTES_SCHEMA` (`claude_runner.py`), so the `structured_output` holds one `tag` / `realization` entry per note of the `.pd`. `MainWindow._show_result` routes the structured output by its key (`notes` to `_save_notes`, `steps` to `_show_parity`). A result belongs to the graph the run started on (`_run_path`), which need not be the open one any more: notes are written beside that graph, and verdicts are dropped if another graph is open. `_save_notes` writes it as JSON `{tag: text}` to `<name>.notes` beside the graph (`NOTES_SUFFIX`; `source_map` skips that suffix), replacing the previous one. `_show_selection` reads the file on every selection change and, while a single note node is selected (`NOTE_KINDS`), shows its text in `_note_label` above the code view; both sit in `_code_pane`, the right half of the splitter. The text describes the last generation and is not cleared when the note is edited.
- **The parity check answers in structured output and marks the boxes.** `PARITY_ARGS` passes `--json-schema` with `PARITY_SCHEMA` (`claude_runner.py`), so the final `result` event carries a `structured_output` dict: one entry per step tag with a `status` (`match`, `mismatch`, `unimplemented`) and a `reason`, plus `other` for code without a step. `ClaudeRunner.result` emits it; `MainWindow._show_parity` lists it in the log and writes it as JSON to `<name>.issues` beside the graph the run started on (`ISSUES_SUFFIX`; `source_map` skips that suffix): `{"steps": {tag: {status, reason, step}}, "other": [...]}`, matches included, where `step` is the step's item of the description that was checked (`export.tagged_items` on `_run_text`). The badges come only from that file: `_show_issues` (on every undo-stack change, text edit and rescan) calls `NodeItem.set_parity` on the node whose id starts with the tag, but only while the canvas still yields the same item for it, so a change to a step (title, cases, links, notes, groups) hides its verdict, undoing the change shows it again, and a move alone does not. There are no modification times. `set_parity` paints a badge from `PARITY_MARKS` (`items.py`, keys must match the schema's enum) on the top right corner with the reason as tooltip. The badge is outside `shape()`, so it takes no clicks. A generation gets the verdicts that still hold (not the matches) and the `other` lines as a `Parity Issues:` section after the description on stdin (`export.issues_section`, added in `_run_claude`; it is not written to the `.pd`), and `INSTRUCTIONS` tells it to fix them: change both together. A finished generation deletes the file (`_save_notes`), because the code it describes was rewritten.
- **The recent-files list lives in `QSettings`** (`ORG_NAME` / `APP_NAME`, so the registry under `HKCU\Software\PraeceptaFlow` on Windows), key `recentFiles`, newest first, at most `MAX_RECENT`. `MainWindow` takes an optional `settings` argument so tests can pass an INI-backed `QSettings` instead of touching the registry. `open_file` and `save_file` add the path; a failed open removes it.
- **The code pane maps the tag comments back to nodes.** `MainWindow._update_code_view` rescans the folder: after Claude finishes, after save/open and when the window becomes active (`changeEvent`, for edits made in another program). A selection change only runs `_show_selection`, which reads no source files, because Qt emits `selectionChanged` once per item. The pane (`CodeView` inside `_code_pane`, the right half of the central `QSplitter`, first show 50/50, afterwards the splitter keeps the user's width) stays open as long as the folder holds tagged source code or the graph has a `.notes` file (`_has_code` / `_has_notes`, set by the rescan) and View > Source Code is on; it never opens or closes on a selection change, because that shifts the canvas. Without either, selecting a note shows nothing. `source_map.scan` walks the folder of the `.pfg` recursively (skips `.pd`/`.pfg`/`.notes`/`.issues`/`.md`, dot directories, `__pycache__`, `node_modules`, `venv`, files over 1 MB, non-UTF-8 files) and parses the tag/end comments with one language-independent regex (`INSTRUCTIONS` in `instructions.py` defines the format: change both together). A section runs from its tag comment to its end comment, both included; a start without an end runs to the next start of the same tag or the end of the file. A tag belongs to a node if the node id starts with it; the same holds for a logical group (`RegionItem.id`), whose section encloses those of its steps, so `_show_selection` passes the id of a single selected node or region to `highlight`. `CodeView.set_files` renders every file that has a section, whole, sorted by path, under a bold path line, syntax-coloured by Pygments (whole file lexed once so multi-line strings stay correct); it only rebuilds when the text changed and keeps the scroll position. `CodeView.highlight(node_id)` does not touch the document: it sets `ExtraSelection`s (background tint over the node's sections, grey foreground over the rest) and scrolls to the node's first section unless that section is already fully visible. With no node, a note or a step without code there are no selections and the scroll position stays. Qt only repaints extra selections whose range changed, so never change just the format of a selection with an unchanged range. Every rescan reads the whole folder (no cache).
- **`EditorScene.reset()` clears the undo stack before clearing the scene.** Commands hold references to items that `QGraphicsScene.clear()` deletes on the C++ side; keep that order.
- **Focus ends a text edit.** Editing stops on focus loss, so code that needs the current text committed (save, the unsaved-changes prompt) calls `scene.setFocusItem(None)` first. The Delete action is skipped while `scene.is_editing_text()` is true.
- **A node's title ignores the mouse unless it is being edited**, so clicks and drags on it reach the node. `EditableText` toggles `setAcceptedMouseButtons` when editing starts and ends.
- **The view must be shown before fitting.** `EditorView.fit_all()` depends on the real viewport size, which is why `main.py` calls `window.show()` before `open_file()`.

## Dependencies and licensing

The project itself is licensed under GPL-3.0-or-later (`LICENSE`).

`requirements.txt` lists `PySide6-Essentials` rather than `PySide6` on purpose: Essentials contains only LGPL-licensed Qt modules. Adding `PySide6-Addons` or the full `PySide6` package brings in GPL-only modules (Qt Charts, Qt Graphs and others), so check a module's license before depending on it. `Pygments` (BSD) provides the syntax highlighting in the code pane.
