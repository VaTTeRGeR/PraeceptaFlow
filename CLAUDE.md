# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

PraeceptaFlow: a prototype desktop editor for flow graphs that represent program structure, built on PySide6's Graphics View framework. Windows is the development platform; the helper scripts are `.bat` files.

## Commands

All commands use the project venv at `.venv` (Python 3.14, which requires PySide6 6.10 or later).

| Task | Command |
|---|---|
| Run the app | `run.bat [file.pfg]` (no console window, uses `pythonw.exe`) |
| Run the app with a console | `run_console.bat [file.pfg]` or `.venv\Scripts\python.exe src\main.py [file.pfg]` |
| Install dependencies | `.venv\Scripts\python.exe -m pip install -r requirements.txt` |
| Build a PyInstaller bundle | `build.bat [--onefile]` (creates the venv if missing, installs `requirements-build.txt`) |
| Remove `build\` and `dist\` | `clean.bat` |

There is no test suite and no linter configured.

`build.bat` predates the GUI: it names the output `PraeceptaFlow` but still builds a console executable (no `--windowed`). `*.spec` files are git-ignored and regenerated by PyInstaller.

### Checking GUI changes without a display

Set `QT_QPA_PLATFORM=offscreen`, construct `MainWindow`, and drive it with `PySide6.QtTest.QTest`. Two things to know:

- The offscreen platform has no fonts, so text renders as boxes and text widths are wrong. Use the native platform for screenshots (`widget.grab().save(...)`).
- `QTest.mouseDClick` sends a bare double-click event. Qt's scene turns that into a plain press unless the same item received the preceding press, so simulate a real double-click as `mouseClick`, then `mouseDClick`, then `mouseRelease`.

## Architecture

`src/main.py` is the entry point and is run as a script, so `src/` is the import root: modules import each other as `from editor.x import ...`, not `from src.editor...` and not relatively. PyInstaller relies on the same layout.

The editor lives in `src/editor/`:

- **`items.py`**: the graphics items. `NodeItem` is a box centred on its position with a title and a wide border (`BORDER_WIDTH`) that edges are dragged from. `EdgeItem` is a curved arrow between an anchor on each node's outline, leaving each node at a right angle. `EdgeHandle` is the draggable circle at each end (the node's body is cut out of the painted circle, so it looks half-hidden). `EditableText` is the base for in-place text editing (currently only the node title). The title is multi-line and centred: Enter inserts a line break, Ctrl+Enter or Escape ends the edit. Qt only centres lines within a fixed text width, so `NodeItem._layout` sets the title's text width to its widest line (measured unbounded first, or the old width would wrap typing) and runs on `contentsChanged`, because with a fixed width `documentSizeChanged` no longer fires when the text shrinks.
- **`scene.py`**: `EditorScene` owns the mouse interaction (dragging from a node's border to create an edge, recording moves), the grid background, and `to_dict` / `load_dict`.
- **`view.py`**: `EditorView` handles zoom and pan only.
- **`commands.py`**: the `QUndoCommand` subclasses.
- **`export.py`**: `project_description`, which turns the dict from `EditorScene.to_dict` into the text of a project description (`*.pd`). It works on the dict, not on scene items.
- **`claude_runner.py`**: `ClaudeRunner`, which runs `claude -p` (stream-json) in a folder and turns its events into lines of text; `ClaudeSetup`, which checks the install and login and lists the models; also holds the two prompts.
- **`instructions.py`**: `INSTRUCTIONS`, the system prompt for those runs as a string constant, so it is part of the app (and of a PyInstaller bundle) instead of a file to locate.
- **`source_map.py`**: finds the tag comments in the generated source files (no Qt); `scan(folder)`.
- **`code_view.py`**: `CodeView`, the read-only code pane: whole files, syntax colours from Pygments, the selected node's code tinted and the rest grey.
- **`main_window.py`**: menus, file handling and modified-state tracking.

### Things that span several files

- **There is no separate graph model.** The scene items are the document. Each item has `to_dict` / `from_dict`, and `EditorScene.to_dict` / `load_dict` assemble the file (JSON, `*.pfg` for "ProjectFlowGraph", with a `version` field checked against `FORMAT_VERSION`). Introducing a view-independent model is the intended next step before validation or code generation.
- **All structural changes go through the undo stack.** Add, delete and move push a command onto the `QUndoStack` created in `MainWindow` and shared with the scene. Commands call `EditorScene.add_item` / `remove_item`, never `addItem` / `removeItem` directly, because those two methods also maintain each node's `edges` list.
- **Box types are a field, not classes.** `NodeItem.kind` is a `NodeKind` from the `NODE_KINDS` table in `items.py` (label, `color`, `outgoing`, `incoming`, `arrow_head`), stored in the file as the table key in the node's optional `type` field (`DEFAULT_KIND` when absent). The label is painted on the top border, which takes the kind's `color`; the body is a light tint of it. The selection ring is drawn outside the box so the colour stays visible when selected. `connection_error` is the one place that decides whether an edge is allowed; the scene's edge drag and `EdgeItem.from_dict` both use it. An edge drops its arrow head (`EdgeItem.has_head`) if either end's kind has `arrow_head=False`. The Insert menu is generated from the table.
- **Edges are tracked on both ends.** `NodeItem.edges` lists every attached `EdgeItem`; the node calls `edge.update_path()` when it moves or its size changes. `DeleteItemsCommand` uses the same list to remove and restore the edges of a deleted node.
- **Edge handles are separate scene items.** Each `EdgeItem` owns two `EdgeHandle`s that `EditorScene.add_item` / `remove_item` add and remove with it. They sit above the nodes (z=2; the edge itself is at z=-1) because their circle overlaps the node's border, and `EditorScene.mousePressEvent` lets a press on a handle through instead of starting a new edge. Dragging one slides that end along the same node's outline and pushes a `MoveAnchorCommand`.
- **Edge ends are anchors, not fixed points.** An anchor is a point on the node's outline stored as fractions of the box's half size (one coordinate is always ±1), so it keeps its relative place when the title changes the box size. `NodeItem.anchor_at` / `anchor_pos` convert to and from scene positions. The anchor lies on the bounding rectangle, but the part of a side within `CORNER_RADIUS` of a corner is bent onto the rounded corner (`_outline_point`), so the edge leaves at an angle between 0° and 45° there; `anchor_normal` gives that direction. The file stores them as optional `source_anchor` / `target_anchor` pairs; an edge without them gets anchors facing the other node at load time.
- **The canvas context menu is the Insert menu.** `EditorView.contextMenuEvent` emits `canvas_context_menu` for a right-click on empty background, and `MainWindow._show_canvas_menu` execs the same `QMenu` the menu bar uses, so new Insert actions appear in both. `MainWindow._insert` places the new item at the click (`_insert_pos`) or, for a shortcut, at the pointer if it is over the viewport (`_pointer_scene_pos`), snapped to the grid. Picks from the menu bar fall back to the view centre with a stagger, because the pointer is then over the dropdown (`_insert_menu_open` tracks that).
- **Text edits bypass the undo stack.** `EditableText` emits `EditorScene.text_edited` when an edit ends with changed text, and `MainWindow` keeps a separate `_text_dirty` flag. The window is modified when that flag is set or the undo stack is not clean.
- **The project description (`*.pd`) is derived from the graph and rewritten on every save, every open and on close.** `MainWindow._export_beside` writes it next to the `.pfg` (a failure is reported but the save or open still succeeds); there is no menu item. On close it is only rewritten when the window is not modified, so discarding changes leaves the `.pd` matching the file on disk. It is plain text made of lists: `Project Notes:` first, then the tooling notes that are not connected to a step, then `Program Flow:` with one item per step (the kinds in `STEP_KINDS`), then the implementation notes that are not connected to a step. A step is identified by a hash, the first `MIN_HASH_LENGTH` characters of the node's id (longer for all nodes if two would collide), and names the steps its edges lead to under `Next:` (`end` if there are none). A step's whole title stays together as one list item (further lines continue it); `Next:` and the note headings are plain indented lines, not list items. Every note item (project notes too) also starts with its own hash, which is only there so a generation can report on the note; it never appears in source code. `INSTRUCTIONS` in `instructions.py` documents this format for the agent, so change both together. Implementation and tooling notes (`NOTE_HEADINGS`) are listed under every step they share an edge with, whichever end they are on. Steps are in flow order (topological, ties and cycles by position, top to bottom).
- **The Source Generation menu runs Claude Code on the `*.pd`.** `Generate Source Code` (Ctrl+G) pipes the description to `claude -p` with `INSTRUCTIONS` appended to the system prompt (`--append-system-prompt`), in the `.pd`'s folder, with `acceptEdits`. `Check Parity` (Ctrl+Shift+G) uses the same instructions but a prompt that only compares source and description; edit and shell tools are denied. Both save first (`_maybe_save`), need a saved graph, and log what Claude says and which tools it uses into the bottom "Claude" dock (View menu toggles it). The `claude` command must be on `PATH`. Closing the window while it runs asks, then kills the process. The same menu has `Model` and `Effort` submenus whose choices are appended as `--model` / `--effort` to both commands (`MainWindow._model_args`); "Default" passes no flag, so the user's own claude settings decide, and the choice is not persisted. The lists are not hard-coded: `ClaudeSetup` (`claude_runner.py`, started by `main.py` through `MainWindow.start_claude_check`) checks that `claude` is on `PATH`, that `claude auth status --json` says `loggedIn`, then sends the stream-json `initialize` control request (claude has no model-listing command) and uses the `models` of the reply (`value`, `displayName`, `supportsEffort`, `supportedEffortLevels`). A problem is shown as a dialog (with a Log in button that runs `claude auth login` and re-checks); until claude answers, or if it cannot, both submenus only hold "Default". The effort menu is rebuilt from the selected model's levels and disabled for models without effort support.
- **A generation reports how each note was realized.** `GENERATE_ARGS` passes `--json-schema` with `NOTES_SCHEMA` (`claude_runner.py`), so the `structured_output` holds one `tag` / `realization` entry per note of the `.pd`. `MainWindow._show_result` routes the structured output by its key (`notes` to `_save_notes`, `steps` to `_show_parity`). `_save_notes` writes it as JSON `{tag: text}` to `<name>.notes` beside the graph (`NOTES_SUFFIX`; `source_map` skips that suffix), replacing the previous one. `_update_code_view` reads the file on every refresh and, while a single note node is selected (`NOTE_KINDS`), shows its text in `_note_label` above the code view; both sit in `_code_pane`, the right half of the splitter. The text describes the last generation and is not cleared when the note is edited.
- **The parity check answers in structured output and marks the boxes.** `PARITY_ARGS` passes `--json-schema` with `PARITY_SCHEMA` (`claude_runner.py`), so the final `result` event carries a `structured_output` dict: one entry per step tag with a `status` (`match`, `mismatch`, `unimplemented`) and a `reason`, plus `other` for code without a step. `ClaudeRunner.result` emits it; `MainWindow._show_parity` lists it in the log and calls `NodeItem.set_parity` on the node whose id starts with the tag, which paints a badge from `PARITY_MARKS` (`items.py`, keys must match the schema's enum) on the top right corner with the reason as tooltip. The badge is outside `shape()`, so it takes no clicks. Verdicts are not saved, and `_clear_parity` removes them on any undo-stack change (a move too), any text edit and at the start of every claude run.
- **The recent-files list lives in `QSettings`** (`ORG_NAME` / `APP_NAME`, so the registry under `HKCU\Software\PraeceptaFlow` on Windows), key `recentFiles`, newest first, at most `MAX_RECENT`. `MainWindow` takes an optional `settings` argument so tests can pass an INI-backed `QSettings` instead of touching the registry. `open_file` and `save_file` add the path; a failed open removes it.
- **The code pane maps the tag comments back to nodes.** `MainWindow._update_code_view` runs on selection change, after Claude finishes and after save/open. The pane (`CodeView` inside `_code_pane`, the right half of the central `QSplitter`, first show 50/50, afterwards the splitter keeps the user's width) stays open as long as the folder holds tagged source code and View > Source Code is on; it does not follow the selection. `source_map.scan` walks the folder of the `.pfg` recursively (skips `.pd`/`.pfg`, dot directories, `__pycache__`, `node_modules`, `venv`, files over 1 MB, non-UTF-8 files) and parses the tag/end comments with one language-independent regex (`INSTRUCTIONS` in `instructions.py` defines the format: change both together). A section runs from its tag comment to its end comment, both included; a start without an end runs to the next start of the same tag or the end of the file. A tag belongs to a node if the node id starts with it. `CodeView.set_files` renders every file that has a section, whole, sorted by path, under a bold path line, syntax-coloured by Pygments (whole file lexed once so multi-line strings stay correct); it only rebuilds when the text changed and keeps the scroll position. `CodeView.highlight(node_id)` does not touch the document: it sets `ExtraSelection`s (background tint over the node's sections, grey foreground over the rest) and scrolls to the node's first section unless that section is already fully visible. With no node, a note or a step without code there are no selections and the scroll position stays. Qt only repaints extra selections whose range changed, so never change just the format of a selection with an unchanged range. The folder is rescanned on every refresh (no cache).
- **`EditorScene.reset()` clears the undo stack before clearing the scene.** Commands hold references to items that `QGraphicsScene.clear()` deletes on the C++ side; keep that order.
- **Focus ends a text edit.** Editing stops on focus loss, so code that needs the current text committed (save, the unsaved-changes prompt) calls `scene.setFocusItem(None)` first. The Delete action is skipped while `scene.is_editing_text()` is true.
- **A node's title ignores the mouse unless it is being edited**, so clicks and drags on it reach the node. `_TitleText` toggles `setAcceptedMouseButtons` when editing starts and ends.
- **The view must be shown before fitting.** `EditorView.fit_all()` depends on the real viewport size, which is why `main.py` calls `window.show()` before `open_file()`.

## Dependencies and licensing

The project itself is licensed under GPL-3.0-or-later (`LICENSE`).

`requirements.txt` lists `PySide6-Essentials` rather than `PySide6` on purpose: Essentials contains only LGPL-licensed Qt modules. Adding `PySide6-Addons` or the full `PySide6` package brings in GPL-only modules (Qt Charts, Qt Graphs and others), so check a module's license before depending on it. `Pygments` (BSD) provides the syntax highlighting in the code pane.
